\section{Implementacja komponentu renderującego}
% https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf s. 745
Implementację można podzielić w logiczny sposób na trzy główne etapy: inicializacja okna, inicializajcja WebGPU, oraz pętla główna aplikacji. Etapy inicjalizacji muszą być wykonywane w określonej kolejności, dlatego naturalnie układają się w potok. Jednak inaczej niż w typowym potoku zamiast przekazywać między etapami dane, zostanie przekazyawana informacja o sukcesie lub błędzie inicjalizacji poszczególnego elementu. W razie wystąpienia błędu, potok zostanie przerwany, a informacja o błędzie wyświetlona. Jest to system podobny w swoim działaniu to wyjątków, jednak dużo bardziej wydajny. Standard C++23 dostarcza do biblioteki standardowej obiekt \texttt{std::expected<T1, T2>}, który spełnia wyżej wymienioną funkcjonalność. Użyta zostanie specjalizacja \texttt{std::expected<void, std::string>}, gdzie pierwszy parametr szablonu \texttt{void} symbolizuje brak danych zwracanych w przypadku sukcesu, a drugi parametr \texttt{std::string}, przechowuje komunikat o błędzie. Jak można zauważyć na poniższym listingu, głowna funkcja inicializująca skłąda się z dwóch z trzech wcześniej wymienionych etapów, ponieważ pętla głowna wykonywana jest po zakończeniu poprawnej inicjalizacji. %monadic operations
\begin{lstlisting}[caption={Funkcja inicjalizująca komponent renderujący}, label={lst:initialize}]
void
initialize()
{
  auto result = init_window()
    .and_then([ this ]() { return init_renderer(); })
  
  if (!result.has_value())
  {
    std::println(
      std::cerr, "Error occured:\n{}", result.error());
    std::exit(1);
  }
}
\end{lstlisting}

\subsection{Okno apliakcji}
Pierwszym etapem jest utworzenie okna aplikacji, w którym będzie wyświetlany renderowany obraz. W tym celu wykorzystano bibliotekę GLFW, która umożliwia tworzenie okien oraz obsługę zdarzeń wejściowych w sposób niezależny od platformy. Proces inicjalizacji okna obejmuje inicializację biblioteki, oraz stworzenie okna. Wskaźnik na utworzone okno jest zapisywany w klasie głównej aplikacji. Opcjonalnie można też narzucić minimalny rozmiar okna lub wymusić stałą proporcję, co ułatwia utrzymanie spójnej perspektywy w czasie demonstracji.
\begin{lstlisting}[caption={Część kodu odpowiedzialna za inicializację okna}, label={lst:init_window}]
auto
init_window() -> std::expected<void, std::string>
{
  if (glfwInit() == GLFW_FALSE)
  {
    return std::unexpected { "Failed to initialize GLFW" };
  }
  glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);
  glfwWindowHint(GLFW_RESIZABLE, GLFW_TRUE);
  p_window =
    glfwCreateWindow(
        initial_width, initial_height, 
        "INZ", nullptr, nullptr);
  if (p_window == nullptr)
  {
    return std::unexpected { "Failed to create window" };
  }
  glfwSetWindowUserPointer(p_window, this);
  // ...
}
\end{lstlisting}
Reszta kodu w tej funkcji odpowiada za ustawienie asynchronicznych funkcji obsługi zdarzeń, takie jak zmiana rozmiaru okna czy obsługa myszy.
\begin{lstlisting}[caption={Dalsza część funkcji inicializującej okno - obsługa pozycji myszy}, label={lst:init_window_cursor}]
auto
init_window() -> std::expected<void, std::string>
{
  // ...
  glfwSetCursorPosCallback(
    p_window,
    [](GLFWwindow* window, double x_pos, double y_pos)
    {
      if (auto* app = reinterpret_cast<application*>(
        glfwGetWindowUserPointer(window)); app != nullptr)
      {
        app->cursor_position_callback(x_pos, y_pos);
      }
    });
}
\end{lstlisting}

\subsection{WebGPU}
Inicjalizacja WebGPU składa się z trzynastu kroków, które muszą być wykonane w określonej kolejności, aby poprawnie skonfigurować środowisko renderujące. Poniżej przedstawiono poszczególne kroki wraz z opisem ich funkcji. W praktyce są one łączone w potok oparty na \texttt{std::expected} i operacjach \texttt{and\_then}, co umożliwia natychmiastowe przerwanie przy pierwszym błędzie oraz czytelne przesłanie komunikatu o niepowodzeniu.
%cos dodac
%init_renderer()
\begin{lstlisting}[caption={Funkcja inicializująca WebGPU, stworzona jako potok}, label={lst:init_renderer}]
auto
init_renderer() -> std::expected<void, std::string>
{
  return init_adapter()
    .and_then([ this ] { return init_device(); })
    .and_then([ this ] { return init_queue(); })
    .and_then([ this ] { return init_shader_module(); })
    .and_then([ this ] { return init_depth_texture(); })
    .and_then([ this ] { return init_bind_group_layout(); })
    .and_then([ this ] { return init_pipeline(); })
    .and_then([ this ] { return init_sampler(); })
    .and_then([ this ] { return init_textures(); })
    .and_then([ this ] { return init_geometry(); })
    .and_then([ this ] { return init_uniforms(); })
    .and_then([ this ] { return init_lighting_uniforms(); })
    .and_then([ this ] { return init_bind_group(); });
}
\end{lstlisting}

\subsubsection{Adapter}
%https://www.w3.org/TR/webgpu/#adapters
Adapter to reprezentacja fizycznego lub wirtualnego urządzenia GPU dostępnego w systemie. W tym kroku aplikacja wysyła zapytanie do systemu o dostępne adaptery, a następnie wybiera najbardziej odpowiedni na podstawie określonych kryteriów, takich jak wydajność czy obsługiwane funkcje. Aby móc uzyskać adapter, należy najpierw utworzyć instancję WebGPU (\texttt{WGPUInstance}), która stanowi globalny punkt wejścia do interfejsu WebGPU i reprezentuje implementację tego API w systemie. Następnie tworzona jest powierzchnia renderująca (\texttt{WGPUSurface}), która stanowi abstrakcję powiązaną z wcześniej zainicjalizowanym oknem GLFW i umożliwia prezentację wyrenderowanych obrazów użytkownikowi. Powierzchnia ta jest przekazywana jako parametr opcji adaptera (\texttt{compatibleSurface}), dzięki czemu wybierany adapter będzie kompatybilny z docelową powierzchnią renderowania. Dopiero po utworzeniu instancji i powierzchni możliwe jest wysłanie zapytania o adapter spełniający określone kryteria kompatybilności.
%kod init_adapter()
\begin{lstlisting}[caption={Funkcja inicializująca obiekt adapter}, label={lst:init_adapter}]
auto
init_adapter() -> std::expected<void, std::string>
{
  m_instance = wgpuCreateInstance(nullptr);
  if (m_instance == nullptr)
  {
    return std::unexpected { "Failed to initialize WebGPU" };
  }
  m_surface = glfwCreateWindowWGPUSurface(m_instance, p_window);
  if (m_surface == nullptr)
  {
    return std::unexpected { "Failed to initialize surface" };
  }
  wgpu::RequestAdapterOptions adapter_options {};
  adapter_options.compatibleSurface = m_surface;
  m_adapter = m_instance.requestAdapter(adapter_options);
  if (m_adapter == nullptr)
  {
    return std::unexpected { "Failed to create adapter" };
  }
  return {};
}
\end{lstlisting}

\subsubsection{Urządzenie}
%https://www.w3.org/TR/webgpu/#devices
Urządzenie to logiczne przedstawienie wybranego adaptera, które umożliwia tworzenie zasobów procesora graficznego oraz wykonywanie operacji renderujących. W tym kroku aplikacja tworzy obiekt \texttt{WGPUDevice}, który będzie używany do komunikacji z procesorem graficznym. Przed jego utworzeniem z adaptera odczytywane są wspierane limity (\texttt{WGPULimits}), a następnie definiowany jest zestaw wymaganych limitów przekazywany w deskryptorze urządzenia. Limity te określają oczekiwania aplikacji względem: organizacji geometrii (np. liczby i struktury atrybutów oraz buforów wierzchołków), poprawnych przesunięć dla operacji na pamięci, przepływu danych między etapami shadera (uniformy), a także modelu powiązań zasobów. Obejmują również ograniczenia dotyczące tekstur i samplerów (wymiary oraz liczebność na etap), tak aby odpowiadały realnym wymaganiom potoku i używanych materiałów. Dzięki zastosowaniu limitów urządzenie jest tworzone tylko wtedy, gdy implementacja WebGPU gwarantuje parametry wystarczające do bezpiecznego i wydajnego działania. W \texttt{WGPUDeviceDescriptor} ustawiane są ponadto etykiety, wskaźnik do wymaganych limitów, opis domyślnej kolejki oraz funkcje zwrotne dla utraty urządzenia i błędów nieprzechwyconych, które służą diagnostyce. Po utworzeniu urządzenia dobierany jest format powierzchni (\texttt{BGRA8Unorm}) i wykonywana jest konfiguracja (\texttt{configure\_surface()}), aby zapewnić poprawne wyświetlanie na utworzonej wcześniej powierzchni.
%kod init_device()
\begin{lstlisting}[caption={Funkcja inicializująca obiekt device}, label={lst:init_device}]
auto
init_device() -> std::expected<void, std::string>
{
  auto required_limits = get_limits(m_adapter);
  wgpu::DeviceDescriptor device_descriptor {};
  // ...

  m_device = m_adapter.requestDevice(device_descriptor);
  if (m_device == nullptr)
  {
    return std::unexpected { "Failed to create device" };
  }
  m_surface_format = wgpu::TextureFormat::BGRA8Unorm;
  configure_surface();
  return {};
}
\end{lstlisting}

\subsubsection{Zasoby tworzone przez urządzenie}
Po utworzeniu urządzenia (\texttt{WGPUDevice}) większość pozostałych zasobów procesora graficznego jest tworzona za jego pomocą. Proces inicjalizacji tych zasobów podąża za wspólnym wzorcem: najpierw tworzony jest obiekt deskryptora, który zawiera szczegółową konfigurację zasobu, następnie wywoływana jest odpowiednia funkcja, która zwraca gotowy zasób. Takie podejście zapewnia spójność i czytelność kodu, a także ułatwia diagnostykę problemów poprzez sprawdzenie, czy zwrócony wskaźnik nie jest pustym wskaźnikiem.

\paragraph{Kolejka poleceń}
Kolejka poleceń (\texttt{WGPUQueue}) jest uzyskiwana bezpośrednio z urządzenia bez potrzeby tworzenia deskryptora. Dzięki kolejce kod aplikacji wykonywany na procesorze komputera może wysyłać polecenia do procesora graficznego w sposób asynchroniczny.

\paragraph{Moduł shaderów}
Moduł shaderów zawiera skompilowany kod shaderów napisanych w języku WGSL. Shadery definiują sposób przetwarzania wierzchołków (vertex shader) oraz obliczania koloru pikseli (fragment shader). W implementacji kod shaderu jest ładowany z pliku za pomocą funkcji pomocniczej \texttt{load::shader\_module()}, która wewnętrznie wykorzystuje \texttt{device.createShaderModule()}.

\paragraph{Tekstura głębi}
Tekstura głębi to specjalny zasób do przechowywania informacji o odległości każdego piksela od kamery w scenie 3D. Jest używana podczas testów głębi w potoku renderowania, aby określić, które fragmenty są widoczne, a które zasłonięte przez bliższe obiekty. W deskryptorze tekstury kluczowe są parametry: \texttt{format} (\texttt{Depth24Plus} - 24-bitowa precyzja głębi), \texttt{usage} (\texttt{RenderAttachment} - użycie jako załącznik renderowania), oraz wymiary odpowiadające wymiarom okna. Po utworzeniu tekstury, tworzony jest także widok tekstury (\texttt{TextureView}) poprzez wywołanie \texttt{texture.createView()}, który jest używany w potoku renderowania.
\begin{lstlisting}[caption={Funkcja inicializująca obiekt depth texture}, label={lst:init_depth_texture}]
auto
init_depth_texture() -> std::expected<void, std::string>
{
  wgpu::TextureDescriptor depth_texture_descriptor = //...
  m_depth_texture = 
    m_device.createTexture(depth_texture_descriptor);
  if (m_depth_texture == nullptr)
  {
    return std::unexpected { "Failed to create depth texture" };
  }
  auto depth_texture_view_descriptor = //...
  m_depth_texture_view =
    m_depth_texture.createView(depth_texture_view_descriptor);
  if (m_depth_texture_view == nullptr)
  {
    return 
      std::unexpected { "Failed to create depth texture view" };
  }
  return {};
}
\end{lstlisting}

\paragraph{Układ grupy powiązań}
Układ grupy powiązań definiuje interfejs między zbiorem zasobów a ich dostępnością w poszczególnych etapach shadera. W deskryptorze określane są typy zasobów (bufory uniformów, tekstury, samplery), ich indeksy powiązań oraz widoczność w shaderach wierzchołków i fragmentów. Jest to schemat określający, jakie zasoby będą dostępne dla shaderów, ale nie zawiera jeszcze konkretnych instancji tych zasobów.

\paragraph{Układ potoku i potok renderowania}
Potok renderowania jest kluczowym elementem procesu renderowania, definiującym wszystkie etapy przetwarzania danych graficznych. Według standardu WebGPU obejmuje on następujące etapy: pobieranie wierzchołków (vertex fetch), shader wierzchołków (vertex shader), składanie prymitywów (primitive assembly), rasteryzacja (rasterization), shader fragmentów(fragment shader), test szablonu i operacje (stencil test and operation), test głębi i zapis (depth test and write), oraz scalanie wyjścia (output merging).

Tworzenie potoku renderowania jest bardziej złożone niż innych zasobów i wymaga wielu struktur konfiguracyjnych. Najpierw tworzony jest układ potoku (\texttt{WGPUPipelineLayout}), który określa ogólną organizację zasobów dostępnych dla shaderów, bazując na wcześniej utworzonym \texttt{WGPUBindGroupLayout}. Następnie wypełniany jest deskryptor potoku renderowania (\texttt{WGPURenderPipelineDescriptor}), który zawiera konfigurację wszystkich wyżej wymienionych etapów. W implementacji poszczególne etapy konfigurowane są przez dedykowane.
\begin{lstlisting}[caption={Funkcja inicializująca obiekt pipeline}, label={lst:init_pipeline}]
auto
init_pipeline() -> std::expected<void, std::string>
{
  auto vertex_attribs = get_vertex_attributes();
  auto vertex_buffer_layout = 
    get_vertex_buffer_layout(vertex_attribs);
  wgpu::RenderPipelineDescriptor pipeline_desc {};
  // Fill vertex and primitive stage
  wgpu::FragmentState fragment_state {};
  wgpu::BlendState blend_state {};
  wgpu::ColorTargetState color_target {};
  // Fill fragment stage
  wgpu::DepthStencilState depth_stencil_state = wgpu::Default;
  // Fill depth-stencil and multisampling stage
  auto pipeline_layout_desc = get_pipeline_layout_desc();
  m_layout = m_device.createPipelineLayout(pipeline_layout_desc);
  pipeline_desc.layout = m_layout;
  m_pipeline = m_device.createRenderPipeline(pipeline_desc);
  if (m_pipeline == nullptr)
  {
    return std::unexpected("Failed to create pipeline");
  }
  return {};
}
\end{lstlisting}

\subsubsection{Sampler}
%https://www.w3.org/TR/webgpu/#samplers
Sampler zakodowywyuje transformacje i informacje dotyczące filtrowania, które mogą być wykorzystane w shaderach do interpretacji danych dotyczących zasobów tekstur. W tym kroku aplikacja tworzy obiekt Sampler, który będzie używany do próbkowania tekstur w shaderach.
%kod init_sampler()
\begin{lstlisting}[caption={Funkcja inicializująca obiekt sampler}, label={lst:init_sampler}]
auto
init_sampler() -> std::expected<void, std::string>
{
  wgpu::SamplerDescriptor sampler_descriptor {};
  sampler_descriptor.addressModeU = wgpu::AddressMode::Repeat;
  sampler_descriptor.addressModeV = wgpu::AddressMode::Repeat;
  sampler_descriptor.addressModeW = wgpu::AddressMode::Repeat;
  sampler_descriptor.magFilter = wgpu::FilterMode::Linear;
  sampler_descriptor.minFilter = wgpu::FilterMode::Linear;
  sampler_descriptor.mipmapFilter = 
    wgpu::MipmapFilterMode::Nearest;
  sampler_descriptor.lodMinClamp = 0.0F;
  sampler_descriptor.lodMaxClamp = 8.0F;
  sampler_descriptor.compare = wgpu::CompareFunction::Undefined;
  sampler_descriptor.maxAnisotropy = 1U;
  std::println("Creating sampler...");
  m_sampler = m_device.createSampler(sampler_descriptor);
  if (m_sampler == nullptr)
  {
    return std::unexpected { "Failed to sampler" };
  }
  return {};
}
\end{lstlisting}

\subsubsection{Textures}
%https://www.w3.org/TR/webgpu/#textures
Tekstura składa się z jednowymiarowych, dwuwymiarowych lub trójwymiarowych tablic danych, które mogą zawierać wiele wartości na element, aby reprezentować takie elementy jak kolory. W tym kroku aplikacja ładuje tekstury z plików oraz tworzy obiekty tekstur, które będą używane w shaderach do mapowania tekstur na modele 3D.
%kod init_textures()
\begin{lstlisting}[caption={Funkcja inicializująca obiekty tekstur}, label={lst:init_textures}]
auto
init_textures(

      .and_then(
        [ this ](auto&& pair) 
        -> std::expected<void, std::string>
        {
          std::tie(m_normal_texture, m_normal_texture_view) =
            std::forward<decltype(pair)>(pair);
          return {};
        });
}
\end{lstlisting}

\subsubsection{Geometry}
%https://www.w3.org/TR/webgpu/#buffers
W tym etapie załadowywane są wszystkie potrzebne dane odnośnie geoemtrii modeli. Dane są przesyłane do procesora graficznego za pomocą buforów. Bufor to blok pamięci, który można wykorzystać w operacjach GPU.
%kod init_geometry()
\begin{lstlisting}[caption={Funkcja inicializująca bufor wierzchołków}, label={lst:init_geometry}]
auto
init_geometry(
  const std::filesystem::path& path
  ) -> std::expected<void, std::string>
{
  return
    load::geometry_obj(path, m_vertex_data)
      .and_then(
        [ this ]()
        { return create_vertex_buffer(m_vertex_data.size()); })
      .and_then(
        [ this ]() -> std::expected<void, std::string>
        {
          m_queue.writeBuffer(
            m_vertex_buffer, 0ULL, m_vertex_data.data(),
            m_vertex_data.size() * 
            sizeof(load::vertex_attributes));
          return {};
        });
}
\end{lstlisting}

\subsubsection{Uniforms}
W tym etapie tworzony zostaje bufor uniformów, który przechowuje dane takie jak macierze modelu, widoku i projekcji. Te dane są przesyłane do shaderów, aby umożliwić odpowiednie przekształcenia i renderowanie sceny 3D.
%kod init_uniforms()
\begin{lstlisting}[caption={Funkcja inicializująca bufor uniformów}, label={lst:init_uniforms}]
auto
init_uniforms() -> std::expected<void, std::string>
{
  wgpu::BufferDescriptor uniform_buffer_descriptor {};
  uniform_buffer_descriptor.size = sizeof(my_uniforms);
  uniform_buffer_descriptor.usage =
    wgpu::BufferUsage::CopyDst | wgpu::BufferUsage::Uniform;
  uniform_buffer_descriptor.mappedAtCreation = 0U;
  m_uniform_buffer = 
    m_device.createBuffer(uniform_buffer_descriptor);
  if (m_uniform_buffer == nullptr)
  {
    return 
      std::unexpected { "Could not create uniform buffer" };
  }
  m_uniforms.model_matrix = glm::mat4x4(1.0);
  m_uniforms.projection_matrix = glm::perspective(
    45.0F * std::numbers::pi_v<float> / 180.0F, 
    640.0F / 480.0F, 0.01F, 50000.0F);
  m_queue.writeBuffer(
    m_uniform_buffer, 0, &m_uniforms, sizeof(my_uniforms));
  update_view_matrix();
  return {};
}
\end{lstlisting}

\subsection{Pętla główna}
W pętli głównej wykonywane są ciągłe aktualizacje sceny oraz renderowanie obrazu. Pętla ta działa do momentu zamknięcia okna aplikacji. W każdej iteracji pętli wykonywane są następujące kroki:
\begin{enumerate}
  \item Obsługa zdarzeń okna
  \item Aktualizacja danych uniformów
  \item Zmiana rozmiaru powierzchni renderującej w przypadku zmiany rozmiaru okna
  \item Pobranie następnego widoku tekstury powierzchni do renderowania i natychmiastowe przerwanie iteracji jeśli takowego nie ma.
  \item Utworzenie enkodera poleceń używanego do nagrywania poleceń procesora graficznego.
  \item Stworzenie obiektu render pass.
        Każda instancja tego obiektu definiuje zestaw zasobów obrazów, zwanych załącznikami, wykorzystywanych podczas renderowania.
  \item Ustawienie wcześniej zainicializowanych elementów: potoku renderujacego, bufora wierzchołkówo raz powiązań uniformów.
  \item Wykonanie polecenia rysowania.
  \item Zakończenie działania obiektu render pass.
  \item Sfinalizowanie nagranych poleceń: przesłanie poleceń do kolejki procesora graficznego.
\end{enumerate}
