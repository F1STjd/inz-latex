\section{Implementacja komponentu renderującego}
% https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2023/n4950.pdf s. 745
Implementację podzielono w logiczny sposób na trzy główne etapy: inicjalizacja okna, inicjalizajcja WebGPU, oraz pętla główna aplikacji. Etapy inicjalizacji wykonywano w określonej kolejności, dlatego naturalnie układały się w potok. Jednak inaczej niż w typowym potoku zamiast przekazywać między etapami dane, przekazywano informację o sukcesie lub błędzie inicjalizacji poszczególnego elementu. W razie wystąpienia błędu, potok zostanie przerwany, a informacja o błędzie wyświetlona. Jest to system podobny w swoim działaniu to wyjątków, jednak dużo bardziej wydajny. Standard C++23 dostarcza do biblioteki standardowej obiekt \texttt{std::expected<T1, T2>}, który spełnia wyżej wymienioną funkcjonalność~\cite{ISO-IEC-14882-2024}. Użyto specjalizacji \texttt{std::expected<void, std::string>}, gdzie pierwszy parametr szablonu \texttt{void} symbolizuje brak danych zwracanych w przypadku sukcesu, a drugi parametr \texttt{std::string}, przechowuje komunikat o błędzie. Na listingu \ref{lst:initialize} widoczne jest że, główna funkcja inicjalizująca składa się z dwóch wcześniej wymienionych etapów, ponieważ pętla głowna wykonywana jest po zakończeniu poprawnej inicjalizacji. %monadic operations
\begin{lstlisting}[caption={Funkcja inicjalizująca komponent renderujący}, label={lst:initialize}]
void
initialize()
{
  auto result = init_window()
    .and_then([ this ]() { return init_renderer(); })
  
  if (!result.has_value())
  {
    std::println(
      std::cerr, "Error occured:\n{}", result.error());
    std::exit(1);
  }
}
\end{lstlisting}

\subsection{Okno aplikcji}
W pierwszym etapie utworzono okno aplikacji, w którym będzie wyświetlany renderowany obraz. W tym celu wykorzystano bibliotekę GLFW, która umożliwia tworzenie okien oraz obsługę zdarzeń wejściowych w sposób niezależny od platformy. Proces inicjalizacji okna obejmuje inicjalizację biblioteki, oraz stworzenie okna. Wskaźnik na utworzone okno jest zapisywany w klasie głównej aplikacji. Opcjonalnie można też narzucić minimalny rozmiar okna lub wymusić stałą proporcję, co ułatwia utrzymanie spójnej perspektywy w czasie demonstracji. Implementację tej części przedstawiono na listingu \ref{lst:init_window}
\begin{lstlisting}[caption={Część kodu odpowiedzialna za inicjalizację okna}, label={lst:init_window}]
auto
init_window() -> std::expected<void, std::string>
{
  if (glfwInit() == GLFW_FALSE)
  {
    return std::unexpected { "Failed to initialize GLFW" };
  }
  glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);
  glfwWindowHint(GLFW_RESIZABLE, GLFW_TRUE);
  p_window =
    glfwCreateWindow(
        initial_width, initial_height, 
        "INZ", nullptr, nullptr);
  if (p_window == nullptr)
  {
    return std::unexpected { "Failed to create window" };
  }
  glfwSetWindowUserPointer(p_window, this);
  // ...
}
\end{lstlisting}
Dalsza część kodu w tej funkcji, przedstawiona na listingu \ref{lst:init_window_cursor}, odpowiada za ustawienie asynchronicznych funkcji obsługi zdarzeń, takie jak zmiana rozmiaru okna czy obsługa myszy.
\begin{lstlisting}[caption={Dalsza część funkcji inicjalizującej okno - obsługa pozycji myszy}, label={lst:init_window_cursor}]
auto
init_window() -> std::expected<void, std::string>
{
  // ...
  glfwSetCursorPosCallback(
    p_window,
    [](GLFWwindow* window, double x_pos, double y_pos)
    {
      if (auto* app = reinterpret_cast<application*>(
        glfwGetWindowUserPointer(window)); app != nullptr)
      {
        app->cursor_position_callback(x_pos, y_pos);
      }
    });
}
\end{lstlisting}

\subsection{WebGPU}
Inicjalizacje WebGPU przedstawiono na listingu \ref{lst:init_renderer}. Składa się z trzynastu kroków, które muszą być wykonane w określonej kolejności, aby poprawnie skonfigurować środowisko renderujące. W dalszej części rozdziału przedstawiono poszczególne kroki wraz z opisem ich funkcji. W praktyce są one łączone w potok oparty na \texttt{std::expected} i operacjach \texttt{and\_then}, co umożliwia natychmiastowe przerwanie przy pierwszym błędzie oraz czytelne przesłanie komunikatu o niepowodzeniu.
%cos dodac
%init_renderer()
\begin{lstlisting}[caption={Funkcja inicjalizująca WebGPU, stworzona jako potok}, label={lst:init_renderer}]
auto
init_renderer() -> std::expected<void, std::string>
{
  return init_adapter()
    .and_then([ this ] { return init_device(); })
    .and_then([ this ] { return init_queue(); })
    .and_then([ this ] { return init_shader_module(); })
    .and_then([ this ] { return init_depth_texture(); })
    .and_then([ this ] { return init_bind_group_layout(); })
    .and_then([ this ] { return init_pipeline(); })
    .and_then([ this ] { return init_sampler(); })
    .and_then([ this ] { return init_textures(); })
    .and_then([ this ] { return init_geometry(); })
    .and_then([ this ] { return init_uniforms(); })
    .and_then([ this ] { return init_lighting_uniforms(); })
    .and_then([ this ] { return init_bind_group(); });
}
\end{lstlisting}

\subsubsection{Adapter}
%https://www.w3.org/TR/webgpu/#adapters
Adapter to reprezentacja fizycznego lub wirtualnego urządzenia GPU dostępnego w systemie. Inicjalizację przedstawiono na listingu~\ref{lst:init_adapter}. W tym kroku aplikacja wysyła zapytanie do systemu o dostępne adaptery, a następnie wybiera najbardziej odpowiedni na podstawie określonych kryteriów, takich jak wydajność czy obsługiwane funkcje~\cite{WebGPU-draft}. Aby móc uzyskać adapter, należy najpierw utworzyć instancję WebGPU (\texttt{WGPUInstance}), która stanowi globalny punkt wejścia do interfejsu WebGPU i reprezentuje implementację tego API w systemie. Następnie tworzona jest powierzchnia renderującą (\texttt{WGPUSurface}), która stanowi abstrakcję powiązaną z wcześniej zainicjalizowanym oknem GLFW i umożliwia prezentację wyrenderowanych obrazów użytkownikowi. Powierzchnia ta jest przekazywana jako parametr opcji adaptera (\texttt{compatibleSurface}), dzięki czemu wybierany adapter będzie kompatybilny z docelową powierzchnią renderowania. Dopiero po utworzeniu instancji i powierzchni możliwe jest wysłanie zapytania o adapter spełniający określone kryteria kompatybilności.
%kod init_adapter()
\begin{lstlisting}[caption={Funkcja inicjalizująca obiekt adapter}, label={lst:init_adapter}]
auto
init_adapter() -> std::expected<void, std::string>
{
  m_instance = wgpuCreateInstance(nullptr);
  if (m_instance == nullptr)
  {
    return std::unexpected { "Failed to initialize WebGPU" };
  }
  m_surface = glfwCreateWindowWGPUSurface(m_instance, p_window);
  if (m_surface == nullptr)
  {
    return std::unexpected { "Failed to initialize surface" };
  }
  wgpu::RequestAdapterOptions adapter_options {};
  adapter_options.compatibleSurface = m_surface;
  m_adapter = m_instance.requestAdapter(adapter_options);
  if (m_adapter == nullptr)
  {
    return std::unexpected { "Failed to create adapter" };
  }
  return {};
}
\end{lstlisting}

\subsubsection{Urządzenie}
%https://www.w3.org/TR/webgpu/#devices
Urządzenie to logiczne przedstawienie wybranego adaptera, które umożliwia tworzenie zasobów procesora graficznego oraz wykonywanie operacji renderujących~\cite{WebGPU-draft}. W tym kroku aplikacja tworzy obiekt \texttt{WGPUDevice}, który będzie używany do komunikacji z procesorem graficznym. Przed jego utworzeniem z adaptera odczytywane są wspierane limity (\texttt{WGPULimits}), a następnie definiowany jest zestaw wymaganych limitów przekazywany przy pomocy deskryptora urządzenia. Limity te określają oczekiwania aplikacji względem: organizacji geometrii (np. liczby i struktury atrybutów oraz buforów wierzchołków), poprawnych przesunięć dla operacji na pamięci, przepływu danych między etapami shadera (uniformy), a także modelu powiązań zasobów. Obejmują również ograniczenia dotyczące tekstur i samplerów (wymiary oraz liczebność na etap), tak aby odpowiadały realnym wymaganiom potoku i używanych materiałów. Dzięki zastosowaniu limitów urządzenie jest tworzone tylko wtedy, gdy implementacja WebGPU gwarantuje parametry wystarczające do bezpiecznego i wydajnego działania. W \texttt{WGPUDeviceDescriptor} ustawiane są ponadto etykiety, wskaźnik do wymaganych limitów, opis domyślnej kolejki oraz funkcje zwrotne dla utraty urządzenia i błędów nieprzechwyconych, które służą diagnostyce. Po utworzeniu urządzenia, zgodnie z kodem na listingu~\ref{lst:init_device}, dobierany jest format powierzchni (\texttt{BGRA8Unorm}) i wykonywana jest konfiguracja (\texttt{configure\_surface()}), aby zapewnić poprawne wyświetlanie na utworzonej wcześniej powierzchni.
%kod init_device()
\begin{lstlisting}[caption={Funkcja inicjalizująca obiekt device}, label={lst:init_device}]
auto
init_device() -> std::expected<void, std::string>
{
  auto required_limits = get_limits(m_adapter);
  wgpu::DeviceDescriptor device_descriptor {};
  // ...

  m_device = m_adapter.requestDevice(device_descriptor);
  if (m_device == nullptr)
  {
    return std::unexpected { "Failed to create device" };
  }
  m_surface_format = wgpu::TextureFormat::BGRA8Unorm;
  configure_surface();
  return {};
}
\end{lstlisting}

\subsubsection{Zasoby tworzone przez urządzenie}
Po utworzeniu urządzenia (\texttt{WGPUDevice}) większość pozostałych zasobów procesora graficznego jest tworzona za jego pomocą. Proces inicjalizacji tych zasobów podąża za wspólnym wzorcem: najpierw tworzony jest obiekt deskryptora, który zawiera szczegółową konfigurację zasobu, następnie wywoływana jest odpowiednia funkcja, która zwraca gotowy zasób. Takie podejście zapewnia spójność i czytelność kodu, a także ułatwia diagnostykę problemów poprzez sprawdzenie, czy zwrócony wskaźnik nie jest pustym wskaźnikiem.

\paragraph{Kolejka poleceń}
Kolejka poleceń (\texttt{WGPUQueue}) jest uzyskiwana bezpośrednio z urządzenia bez potrzeby tworzenia deskryptora~\cite{WebGPU-draft}. Dzięki kolejce kod aplikacji wykonywany na procesorze komputera może wysyłać polecenia do procesora graficznego w sposób asynchroniczny.

\paragraph{Moduł shaderów}
Moduł shaderów zawiera skompilowany kod shaderów napisanych w języku WGSL~\cite{WebGPU-draft}. Shadery definiują sposób przetwarzania wierzchołków (vertex shader) oraz obliczania koloru pikseli (fragment shader). W implementacji kod shaderu jest ładowany z pliku za pomocą funkcji pomocniczej \texttt{load::shader\_module()}, która wewnętrznie wykorzystuje \texttt{device.createShaderModule()}.

\paragraph{Tekstura głębi}
Tekstura głębi to specjalny zasób do przechowywania informacji o odległości każdego piksela od kamery w scenie 3D~\cite{WebGPU-draft}. Jest używana podczas testów głębi w potoku renderowania, aby określić, które fragmenty są widoczne, a które zasłonięte przez bliższe obiekty. W deskryptorze tekstury kluczowe są parametry: \texttt{format} (\texttt{Depth24Plus} - 24-bitowa precyzja głębi), \texttt{usage} (\texttt{RenderAttachment} - użycie jako załącznik renderowania), oraz wymiary odpowiadające wymiarom okna. Po utworzeniu tekstury, tworzony jest także widok tekstury (\texttt{TextureView}) poprzez wywołanie \texttt{texture.createView()}, który jest używany w potoku renderowania (listing~\ref{lst:init_depth_texture}).
\begin{lstlisting}[caption={Funkcja inicjalizująca obiekt depth texture}, label={lst:init_depth_texture}]
auto
init_depth_texture() -> std::expected<void, std::string>
{
  wgpu::TextureDescriptor depth_texture_descriptor = //...
  m_depth_texture = 
    m_device.createTexture(depth_texture_descriptor);
  if (m_depth_texture == nullptr)
  {
    return std::unexpected { "Failed to create depth texture" };
  }
  auto depth_texture_view_descriptor = //...
  m_depth_texture_view =
    m_depth_texture.createView(depth_texture_view_descriptor);
  if (m_depth_texture_view == nullptr)
  {
    return 
      std::unexpected { "Failed to create depth texture view" };
  }
  return {};
}
\end{lstlisting}

\paragraph{Układ grupy powiązań}
Układ grupy powiązań definiuje interfejs między zbiorem zasobów a ich dostępnością w poszczególnych etapach shadera~\cite{WebGPU-draft}. W deskryptorze określane są typy zasobów (bufory uniformów, tekstury, samplery), ich indeksy powiązań oraz widoczność w shaderach wierzchołków i fragmentów. Jest to schemat określający, jakie zasoby będą dostępne dla shaderów, ale nie zawiera jeszcze konkretnych instancji tych zasobów.

\paragraph{Układ potoku i potok renderowania}
Potok renderowania jest kluczowym elementem procesu renderowania, definiującym wszystkie etapy przetwarzania danych graficznych. Według standardu WebGPU obejmuje on następujące etapy: pobieranie wierzchołków (vertex fetch), shader wierzchołków (vertex shader), składanie prymitywów (primitive assembly), rasteryzacja (rasterization), shader fragmentów (fragment shader), test szablonu i operacje (stencil test and operation), test głębi i zapis (depth test and write), oraz scalanie wyjścia (output merging)~\cite{WebGPU-draft}.

Tworzenie potoku renderowania jest bardziej złożone niż innych zasobów i wymaga wielu struktur konfiguracyjnych. Najpierw tworzony jest układ potoku (\texttt{WGPUPipelineLayout}), który określa ogólną organizację zasobów dostępnych dla shaderów, bazując na wcześniej utworzonym obiekcie \texttt{WGPUBindGroupLayout}. Następnie wypełniany jest deskryptor potoku renderowania (\texttt{WGPURenderPipelineDescriptor}), który zawiera konfigurację wszystkich wyżej wymienionych etapów. W implementacji, przedstawionej na listingu~\ref{lst:init_pipeline}, poszczególne etapy konfigurowane są przez dedykowane funkcje pomocnicze.
\begin{lstlisting}[caption={Funkcja inicjalizująca obiekt pipeline}, label={lst:init_pipeline}]
auto
init_pipeline() -> std::expected<void, std::string>
{
  auto vertex_attribs = get_vertex_attributes();
  auto vertex_buffer_layout = 
    get_vertex_buffer_layout(vertex_attribs);
  wgpu::RenderPipelineDescriptor pipeline_desc {};
  // Fill vertex and primitive stage
  wgpu::FragmentState fragment_state {};
  wgpu::BlendState blend_state {};
  wgpu::ColorTargetState color_target {};
  // Fill fragment stage
  wgpu::DepthStencilState depth_stencil_state = wgpu::Default;
  // Fill depth-stencil and multisampling stage
  auto pipeline_layout_desc = get_pipeline_layout_desc();
  m_layout = 
    m_device.createPipelineLayout(pipeline_layout_desc);
  pipeline_desc.layout = m_layout;
  m_pipeline = m_device.createRenderPipeline(pipeline_desc);
  if (m_pipeline == nullptr)
  {
    return std::unexpected("Failed to create pipeline");
  }
  return {};
}
\end{lstlisting}

\paragraph{Sampler}
Sampler koduje informacje dotyczące filtrowania i adresowania tekstur, które są wykorzystywane w shaderach podczas próbkowania (sampling) tekstur~\cite{WebGPU-draft}. W deskryptorze określane są tryby adresowania dla każdej osi (\texttt{Repeat} - powtarzanie tekstury), filtry powiększania i pomniejszania (\texttt{Linear} - interpolacja liniowa dla gładszego wyglądu), oraz parametry poziomów szczegółowości (LOD).

\paragraph{Bufory}
Bufor to blok pamięci procesora graficznego, który może przechowywać różnorodne dane wykorzystywane w operacjach graficznych~\cite{WebGPU-draft}. Wszystkie bufory tworzone są według tego samego wzorca: w deskryptorze określany jest rozmiar bufora, sposób jego użycia (\texttt{usage}) oraz czy ma być mapowany przy tworzeniu. W implementacji używane są trzy rodzaje buforów:
\begin{itemize}
  \item \textbf{Bufor wierzchołków} - przechowuje dane geometrii modeli 3D (pozycje, normalne, współrzędne tekstur). Dane są najpierw ładowane z pliku do pamięci CPU, a następnie przesyłane do bufora procesora graficznego funkcją \texttt{queue.writeBuffer()}. Parametr \texttt{usage}: \texttt{CopyDst | Vertex}.
  \item \textbf{Bufor uniformów transformacji} - przechowuje macierze transformacji (model, widok, projekcja), pozycję kamery oraz dodatkowe parametry renderowania. Macierze te realizują podstawowe transformacje geometryczne: translację, rotację i skalowanie obiektu w przestrzeni 3D~\cite{ji2025}. Jest aktualizowany w każdej klatce, gdy zmienia się perspektywa kamery lub rotacja modelu. Parametr \texttt{usage}: \texttt{CopyDst | Uniform}.
  \item \textbf{Bufor uniformów oświetlenia} - zawiera informacje o źródłach światła w scenie: kierunki świateł, ich kolory oraz parametry modelu oświetlenia (\texttt{kd}, \texttt{ks}, \texttt{hardness}). Parametr \texttt{usage}: \texttt{CopyDst | Uniform}.
\end{itemize}

\paragraph{Tekstury materiałów}
Tekstury to wielowymiarowe tablice danych reprezentujące informacje wizualne, takie jak kolory czy mapy normalnych~\cite{WebGPU-draft}. W implementacji tekstury są ładowane z plików graficznych za pomocą funkcji pomocniczej \texttt{load::texture()}, która wewnętrznie używa \texttt{device.createTexture()} oraz tworzy odpowiedni widok tekstury.

\paragraph{Grupa powiązań}
Grupa powiązań łączy konkretne instancje zasobów (bufory, tekstury, samplery) z ich deklaracjami w układzie grupy powiązań~\cite{WebGPU-draft}. W deskryptorze określany jest wcześniej obiekt \texttt{WGPUBindGroupLayout} oraz tablica wpisów (\texttt{WGPUBindGroupEntry}), z których każdy przypisuje konkretny zasób do odpowiedniego indeksu powiązania, co umożliwia shaderom dostęp do tych zasobów podczas renderowania.

\subsection{Pętla główna}
W pętli głównej wykonywane są ciągłe aktualizacje sceny oraz renderowanie obrazu. Pętla ta działa do momentu zamknięcia okna aplikacji. W każdej iteracji pętli wykonywane są następujące kroki:
\begin{enumerate}
  \item Obsługa zdarzeń okna
  \item Aktualizacja danych uniformów
  \item Zmiana rozmiaru powierzchni renderującej w przypadku zmiany rozmiaru okna
  \item Pobranie następnego widoku tekstury powierzchni do renderowania i natychmiastowe przerwanie iteracji jeśli takowego nie ma.
  \item Utworzenie enkodera poleceń używanego do nagrywania poleceń procesora graficznego.
  \item Stworzenie obiektu render pass.
        Każda instancja tego obiektu definiuje zestaw zasobów obrazów, zwanych załącznikami, wykorzystywanych podczas renderowania.
  \item Ustawienie wcześniej zainicjalizowanych elementów: potoku renderowania, powiązań uniformów oraz bufora wierzchołków.
  \item Wykonanie polecenia rysowania.
  \item Zakończenie działania obiektu render pass.
  \item Sfinalizowanie nagranych poleceń: przesłanie poleceń do kolejki procesora graficznego.
\end{enumerate}
